GitHub binary builds¶

build.yml runs on branch pushes, pull requests and manual dispatch. It calls build-binaries.yml, which builds the CLI using Meson on these runners:

Download the flashrom-* artifacts from the workflow run. Install the Linux package with sudo apt install ./flashrom-*.deb on Ubuntu 24.04 or a compatible newer distribution. On macOS, extract the archive and run ./flashrom from its directory, keeping lib/ beside it. These builds target macOS 15 or later. On Windows, extract the ZIP and run flashrom.exe, keeping its DLLs beside it; MSYS2 is not required on the target.

The macOS executable and bundled libraries are ad-hoc signed after their library paths are rewritten, and each signature is verified before packaging. They are not signed with an Apple Developer ID or notarized. Ad-hoc signing allows local execution but does not establish trust for Gatekeeper: macOS may block files quarantined by a browser download. The CI startup check does not test this download path. Distribution without a Gatekeeper override requires Developer ID signing and Apple notarization.

Builds enable Meson's auto programmer selection and RPMC. Linux includes PCI, USB, FTDI, J-Link and serial dependencies. macOS includes USB, FTDI and serial programmers; Windows also includes J-Link. Internal/PCI programmers are not available on macOS or Windows. USB access on Windows requires the appropriate device driver. The Meson configuration summary lists the actual programmers.

Linux and Windows run the unit tests using GNU linker wrapping, which is not available with the macOS linker. Every job smoke-tests the packaged CLI using --version; Windows clears the toolchain from PATH first, and macOS checks that bundled binaries no longer reference Homebrew libraries. These checks do not test physical programmers.

Releases¶

Update VERSION, commit it with these workflows, tag that commit, and publish a GitHub Release for the tag. Publishing either a release or a prerelease triggers release.yml. It uses the same build and packaging jobs as CI, with the version from VERSION and without a Git suffix. Tag names must refer to commits containing these workflows and the packaging script.

Once all four builds pass, the workflow attaches their packages, a source archive of the release commit, and SHA256SUMS to that release. Only the asset upload job has contents: write; build jobs have read-only access. Assets are not overwritten. If an upload partially fails, remove any assets uploaded by that attempt before rerunning the upload job.

CI packages append the commit ID to their version. Packages include the source commit ID, Meson options and license information. The macOS and Windows builds bundle package-manager libraries and include dependency notices/provenance; Linux relies on distribution packages. Dependency versions follow the runner's package repositories, so rebuilding a tag later is not bit-for-bit reproducible.
